# Current implementation decision

The long-term architecture decision is now [WineD3D-derived semantics with a WebGPU backend](docs/wined3d-feasibility.md). Develop that mode beside the preserved, deprecated custom mode; retain the Theseus CPU and lightweight Win32 environment. This supersedes the earlier restriction below on reconsidering the architecture. The first bounded implementation uses standalone `libvkd3d-shader` for legacy D3D bytecode, Naga for SPIR-V validation and WGSL emission, and the existing WebGPU renderer. It has produced original Humus scene frames; broader WineD3D state semantics and additional applications remain incremental work.

Use pinned Theseus for local original-x86 execution, selected Win32/D3D9 compatibility, MojoShader/Naga for actual shader translation, and hardware WebGPU. The CPU worker communicates with a separate GPU worker through bounded copied draw/upload batches and synchronous boundary replies. The real EXE now renders; the historical first-API blockers below are resolved for the measured subset. See COMPATIBILITY.md and MEASURED-RESULTS.json for current limits and evidence.

The master branch preserves the prior baseline. No working CheerpX rendering baseline or accepted native scene reference is available. Local-only operation remains required pending Theseus redistribution-license clarification. Reconsider the path only for a demonstrated essential execution/API/shader semantic blocker that cannot reasonably be implemented; current work concerns measurement, memory reduction and validation.

## Historical decision record

Selected: local Theseus AOT x86 → generated Rust → WASM, with Win32 compatibility and a future D3D9 → WebGPU frontend. No source port: only the preserved EXE is input to the translator. Theseus commit is pinned in dependencies.json. Reuse its iced-x86 decoder, PE loader, static call graph, indirect-call table, stdcall adapters, Win32 callbacks, filesystem and worker hosting concepts.

Why: this empty repository contains no CheerpX disk, PIC Wine artifact, hosting configuration or recovery scripts. The reported Linux checkpoint is not a rendering baseline. No guest graphics transport has been demonstrated here, so CheerpX+Wine cannot currently be chosen as a working GPU path. Theseus has actual WASM support; its author describes the worker/callback mechanism at https://neugierig.org/software/blog/2026/05/theseus-wasm.html . Its existing pixel-upload host is not a GPU 3D backend and is not used as one.

First milestone (achieved in native and browser tests): execute original startup instructions, follow CRT initialization and model preparation, reach real Direct3DCreate9(31). Unknown imports/instructions must trap with context, not return fake success. First baseline blocker: PE section characteristics 0xc0000240 (LNK_INFO flag); fixed without editing input. Static scanning can mistake data for code, so use --scan-memory only and feed later missing addresses back as entry points. Float80 operations are explicit execution traps, not converted inaccurately to f64.

Missing: accurate required Win32 functions, D3D9 COM implementation, embedded D3DX compiler instruction coverage, SM1/2 bytecode translation, buffer/texture/depth/stencil state and actual WebGPU draw submission. Shader inputs are the application's .shd files. Main.cpp is consulted only as evidence; it is never compiled.

Change-path trigger: executed x86 control flow cannot be recovered without EXE modification, or correct embedded compiler execution proves impractical compared with a licensed existing user-mode runtime. Licensing is also an external deployment blocker: no license declaration was found in Theseus at this revision. Keep its checkout and generated binaries local and untracked; obtain distribution permission or select an explicitly licensed runtime before publishing. Humus readme expressly permits redistribution with readme included; original assets retain the complete archive and structure. iced-x86 declares MIT in Cargo metadata. Cargo.lock from Theseus pins transitive dependencies.

Browser ownership: execution in a dedicated stoppable worker. The future GPU backend belongs in that worker with OffscreenCanvas and direct in-process API calls. Startup host messages are diagnostic only; no per-draw message bridge is claimed. Any 4-hour session must be started by the user and stops on failure, Stop, or its deadline. It cannot override browser suspension.

Shader foundation: consume pinned, unmodified MojoShader locally under its zlib license, with a local adapter; no upstream contribution is made. Its SPIR-V backend requires explicit VS1.1 input declarations and emits combined image/samplers. The adapter supplies declarations from validation reflection without changing shader instructions, then splits sampled-image resources before Naga 30.0.1 validates/emits WGSL. This retains the WebGPU route. Diagnostic draw success is not original-executable acceptance. The first remaining application boundary stays GetDeviceCaps until a device implements its advertised features.
